# Freshness-driven admission control for mixed-criticality vehicular health telemetry

Artifact repository for the paper of the same name: the OMNeT++/Simu5G models,
scenario configurations, campaign drivers and analysis scripts behind every
number in it.

## What is here

| Path | Contents |
|---|---|
| `src/` | The simulation models we wrote: the edge aggregator and its token-bucket admission controller (`src/apps/EdgeApp.{ned,cc}`), the health server, the sensor rig, and the BLE/wired sensor-link models. Source only; `*_m.cc`/`*_m.h` are regenerated by `opp_msgtool` from the `.msg` files at build time. |
| `simulations/` | Scenario configurations, one directory per experiment family. `corridorpop/` holds the seven-corridor population study that the paper's headline and load results come from; `va_case/` and `dc_case/` the rural and urban case studies; `pilot/`, `room/`, `vehicle/`, `validation_ble/` the calibration and validation scenarios. The `towers_*.ini` files carry the eNodeB positions. |
| `tools/` | Campaign drivers (`*.sh`) and analysis scripts (`*.py`). Each result in the paper is regenerated by a named script here — see the table below. |
| `analysis/figures_src/` | Figure scripts. `fig6_oracle_frontier.py` and `fig7_load_effect.py` produce the two figures in the paper, and import the analysis helpers from `tools/` so a figure cannot drift away from the number it illustrates. |
| `analysis/*.csv` | Derived per-run summary tables for the earlier feasibility family. Not the raw corpus. |
| `docs/` | Method and provenance notes: calibration, tower data, corridor sampling, the Simu5G defects, and `CORRECTIONS_2026-10.md`, a log of errors found in our own earlier analyses and what each one changed. |
| `patches/` | A diff against Simu5G tag `v1.4.4` carrying the three defects described in `docs/SIMU5G_PATCHES.md`. |
| `paper/` | The manuscript source, bibliography and figure PDFs. |

## What is not here, and why

The raw simulation output is about 78 GB of OMNeT++ `.sca`/`.vec` files and is
not redistributed. The configurations and campaign drivers that produce it are,
so a campaign can be re-run from scratch; expect the corridor population study
(490 runs) to take on the order of a day on one machine.

The tower extract the corridor geometry derives from is a third-party dataset
and is not redistributed either. `docs/TOWER_DATA.md` records its provenance
and how the corridors were sampled from it, and the resulting eNodeB
coordinates are in the `towers_*.ini` files, so the scenarios run without it.

The repository carries no licence yet. Until one is added, no permissions
beyond viewing are granted.

## Which script produces which result

| Result in the paper | Script |
|---|---|
| Oracle static frontiers; the headline margins | `tools/analyze_static_oracle.py` |
| Load comparison, matched within seed | `tools/analyze_load_effect.py` |
| Signal-source frontiers | `tools/analyze_target_frontier.py` |
| The factorial table | `tools/analyze_deconf.py` |
| Corridor population and strata | `tools/sample_corridors.py` |
| Quality-control checks | `tools/qc_check.py` |
| Figures | `analysis/figures_src/fig6_oracle_frontier.py`, `fig7_load_effect.py` |

## Building

Built against OMNeT++ 6.4.0, INET 4.7.0 and Simu5G 1.4.4 on Linux with clang.
Vehicle traces come from SUMO 1.27 over OpenStreetMap extracts, exported per
second and replayed; `tools/fcd2bonnmotion.py` does that conversion.

```sh
# with a Simu5G 1.4.4 checkout at ../Simu5G
git -C ../Simu5G apply /path/to/patches/simu5g-1.4.4-defects.patch
source /path/to/omnetpp-6.4.0/setenv -q
cd src && make
```

The patch is required: without the path-loss fix the rural line-of-sight links
carry no traffic at all, silently, so the rural corridors produce zero
delivery with no error.

## A note on the correction log

`docs/CORRECTIONS_2026-10.md` lists mistakes we found in our own analyses
during this work, including one that invalidated a whole experimental axis — a
background-traffic parameter bound correctly and instantiated the modules, but
a start-time default meant none of them ever transmitted, so two "load does not
matter" null results had been structurally guaranteed. It is kept in the
repository because a reader checking our numbers should be able to see what we
got wrong and when, not only what survived.
