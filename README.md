# Evidence Delays the Decision, Not the Alert

Artifact repository for the paper of the same name: the OMNeT++/Simu5G models,
scenario configurations, campaign drivers and analysis scripts behind every
number in it.

The paper follows one chain of four steps. A camera-based health monitor's
sensing grade is priced against eight capacity constraints, and the resulting
edge partition is **forced by capacity rather than chosen**. With the inference
local, the verification evidence that justifies an alert turns out not to delay
the **alert** but the **decision** a dispatcher can act on. That cost is linear
in evidence bytes. And a token-bucket gate in front of the evidence — the
machinery such systems inherit — cannot reduce it, which we derive and then
spend 2,160 runs trying to falsify.

> artifact for *From Room to Road: Adapting Edge Traffic for Timely Health
> Monitoring*, which evaluated an adaptive admission controller against tuned
> static baselines. That framing was withdrawn. Its scripts, documents and

> the framing changed. Nothing was deleted to make the new story look tidier.

## What is here

| Path | Contents |
|---|---|
| `src/` | The simulation models: the edge aggregator and its token-bucket admission gate (`src/apps/EdgeApp.{ned,cc}`), the health server, the sensor rig, and the BLE/wired/WLAN sensor-link models. Source only; `*_m.cc`/`*_m.h` are regenerated by `opp_msgtool` at build time. |
| `simulations/` | Scenario configurations, one directory per experiment family. `pilot/` holds the four link conditions and the evidence ladder this paper uses. The `towers_*.ini` files carry the eNodeB positions. |
| `tools/` | Campaign drivers (`*.sh`) and analysis scripts (`*.py`). Every table in the paper is produced by a named script here — see the mapping below. |
| `analysis/*/` | **Verified extracts of the four campaigns.** These are what make the paper reproducible without the raw corpus; see below. |
| `analysis/figures_src/figC*.py` | The paper's five figures. | `docs/` | The result documents the paper cites, the parameter provenance register, and the claim-to-evidence map. |
| `patches/` | **Two** diffs against Simu5G tag `v1.4.4`. `simu5g-1.4.4-defects.patch` carries the three defect fixes in `docs/SIMU5G_PATCHES.md`. `simu5g-scheduling-request.patch` **adds a mechanism the release does not model** — a PUCCH Scheduling Request path — and is required to reproduce these results; see below. |

## Reproducing the paper's tables

**Every table regenerates from the committed extracts alone**, with no raw
simulation output and nothing but the Python standard library:

```sh
python3 -I tools/dispatch_times.py analysis/escalation_vec/escalation_latencies.csv.gz
python3 -I tools/dispatch_times.py analysis/phase2/escalation_latencies.csv.gz
python3 -I tools/edge_contrasts.py        # the 960-run edge-cost campaign
python3 -I tools/gate_contrasts.py        # the 2,160-run gate sweep
```

The figures need `matplotlib` and nothing else:

```sh
python3 -m venv .venv && .venv/bin/pip install matplotlib
for f in analysis/figures_src/figC*.py; do .venv/bin/python "$f"; done
```

### How the extracts relate to the raw corpus

| Campaign | Runs | Raw | Extract here |
|---|---|---|---|
| Evidence ladder (`escalation_vec`) | 600 | 956 MB | 0.4 MB |
| Waveform rung + deferral (`phase2`) | 480 | 766 MB | 0.5 MB |
| Edge cost (`edge`) | 960 | 1.5 GB | 1.1 MB |
| Gate sweep (`gate`) | 2,160 | 3.4 GB | 4.4 MB + 27 KB |

Each extract is a lossless projection of its corpus onto the fields the
analysis reads, checked value-by-value by `tools/verify_extract.py`. For the
gate campaign the equivalence was checked end to end rather than assumed:
`gate_contrasts.py` accepts either input, and the two were confirmed to produce
identical output.

```sh
python3 -I tools/gate_contrasts.py                                 # extract
python3 -I tools/gate_contrasts.py /path/to/results_gate           # raw corpus
```

`analysis/gate/gate_scalars.csv.gz` is the full 54.7 MB scalar extract
projected onto the four counters the sweep actually reads — 27 KB, which is
what keeps this repository clonable. Both are accepted; the small one is
preferred when present.

### Readiness requires the whole burst

`tools/completion.py` is the one to run before trusting any latency number
here. Under the policy the paper models, an escalation missing any chunk never
becomes ready, so every gap figure is a median among **complete** escalations
and is therefore survivorship-biased — the bursts that lost chunks were the
ones the radio treated badly. The completion rate belongs beside every such
figure.

```sh
python3 -I tools/completion.py                                   # Gate A
python3 -I tools/completion.py --expect 99 analysis/gate/escalation_latencies.csv.gz
```

An earlier version of this analysis reported completeness as a fraction of
**bytes**, which is a different and much more flattering quantity: a burst at
E4 is 99 chunks, so 99 % of bytes arriving is consistent with most bursts
being incomplete. `docs/COMPLETION_RESULT.md` records what changed and by how
much.

### A caution carried over from the analysis

`dispatch_times.py` pairs each evidence burst to its escalation on a signed
time window, and **the tolerance matters**. An alert carries its sensing stamp
from the rig while its chunks are stamped at the edge, so the two sit on
different clocks. Too tight a tolerance leaves most escalations unpaired,
silently collapses dispatch onto the alert, and erases the entire effect while
looking plausible — this produced a wrong table once. Always read
`--report-pairing` before the dispatch table, and use `--tol 1.0` on the edge
corpus, where the default 10 ms is wrong.

## What this artifact does not establish

Stated here because the paper states it too, and an artifact that oversells is
worse than one that is modest.

- Everything is **simulated**. No clinical effectiveness, no hardware
  measurement.
- The four link conditions are **named stress cases, not a sample of routes**,
  and their observation windows differ (320 / 1369 / 680 s), so per-escalation
  rates are comparable across them and counts are not.
- The propositions in `docs/GATE_DERIVATION.md` are **derivations from the
  mechanism's definition, not formal proofs**. They rest on two conditions:
  work conservation, asserted of the scheduler and not verified; and a full
  bucket at burst arrival, which *is* checked against the corpus.
- Two of the four per-frame compute costs are **extrapolated** from a different
  vision pipeline and are labelled wherever they appear.
- Four claims in this project were measured, believed, published internally and
  later **withdrawn**. All four are still visible in `docs/`, with the signature
  that exposed each one.

## What is not here, and why

The manuscript itself is not in this repository. It is under submission, and
the venue's policy on prior public posting governs when and where it appears;
this repository is the artifact, not the paper.

The raw simulation output is not redistributed — see the extract table above
for what replaces it. The configurations and campaign drivers that produce it
are here, so any campaign can be re-run from scratch; expect the 2,160-run gate
sweep to take on the order of a day on one machine.

The tower extract the corridor geometry derives from is a third-party dataset
and is not redistributed either. `docs/TOWER_DATA.md` records its provenance,
and the resulting eNodeB coordinates are in the `towers_*.ini` files, so the
scenarios run without it.

## Building

Built against OMNeT++ 6.4.0, INET 4.7.0 and Simu5G 1.4.4 on Linux with clang.
Vehicle traces come from SUMO 1.27 over OpenStreetMap extracts, exported per
second and replayed; `tools/fcd2bonnmotion.py` does that conversion.

```sh
# with a Simu5G 1.4.4 checkout at ../Simu5G
git -C ../Simu5G apply /path/to/patches/simu5g-1.4.4-defects.patch
git -C ../Simu5G apply /path/to/patches/simu5g-scheduling-request.patch
source /path/to/omnetpp-6.4.0/setenv -q
cd src && make
```

**Apply both.** The defect patch is required because without the path-loss fix
the rural line-of-sight links carry no traffic at all, silently, so the rural
scenarios produce zero delivery with no error.

The scheduling-request patch is required for a different and more important
reason: it is not a bug fix but a **missing mechanism we supplied**. Stock
Simu5G models no PUCCH and no Scheduling Request, so a UE with an empty buffer
can only re-acquire a grant via RACH/BSR gated by `retxBsrTimer` — whose LTE
default of 40 subframes is not a standards-legal value, and whose legal values
are all worse. The result is a 320 ms floor on the empty-buffer alert tail that
real LTE does not have. The patch adds the SR path (46 lines, parameters from
TS 36.213 Table 10.1.5-1 and TS 36.331 cl. 6.3.2); every campaign here runs it
at `srPeriod = 5`, `srProhibitTimer = 0`. `srPeriod = 0` is the default and
restores stock behaviour exactly.

**A reproduction that applies only the defect patch will not obtain these
results.** `docs/PARAMETER_PROVENANCE.md` §A.4 records the diagnosis, the
measured timer sweep, and the primary-source ASN.1 the parameter ranges come
from.

**Nothing above needs the simulator.** The analysis and figure commands run
against the committed extracts on a clean checkout.
